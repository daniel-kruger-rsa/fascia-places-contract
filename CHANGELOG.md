# Fascia Places contract — changelog

Every published version of [places.v1.yaml](places.v1.yaml), newest first. A host vendors a
copy pinned to a tag and reads this to decide whether a diff needs its attention.
`scripts/publish-contract.sh` refuses to publish a version that has no entry here.

**"Editorial" means prose only.** A change to any schema node — a type, a nullable, an enum, a required list — is never editorial, however little the wire moves, and gets named on its own line here. We broke that rule on `0.17.1`, and a host caught it by diffing rather than taking our word: a document that does not say what is true has a reader who acts on it anyway.

| Version | Date | Change | Does your client care? |
| --- | --- | --- | --- |
| `0.22.0` | 2026-10-21 | Every entry on `GET /v1/places/layers` now says **which vintage it is of** and whether that vintage still describes what is in force: `vintage`, `superseded_by`, `superseded_from` and **`current`**. Omitted entirely on a layer whose pack records no vintage. | **Yes, if you serve administrative boundaries.** One generation holds layers on different cadences from different custodians — South Africa's wards are a 2020 demarcation and its sub-places a 2011 census, both inside `mdb-zaf-2020` — so the generation name never told you, and nothing else did either. **Branch on `current`,** not on the two date fields: `superseded_by` alone does not mean a layer is wrong, because a census snapshot stays a true description of its own year. The case that forced this: South Africa's ward boundaries are superseded on **4 November 2026**, election day, when 4,468 wards become 4,488. Until now that would have happened with nothing in the data to say so — the same failure as a readiness flag that reports ready while nothing works. `current` is computed per request against the server's date, so it flips on the day without a deployment. |
| `0.21.0` | 2026-10-20 | **South African responses now carry a Stats SA credit**, and `GET /v1/places/generation` gains **`attribution`** — the display duty for that country and generation, read without a host key. An `Attribution` object gains **`statement`**: the full acknowledgement a rights holder has approved, in its own words, where one exists. The pack credit now also rides on `/geojson`, `/area/{area_id}/geojson`, `/area/{area_id}/neighbours`, `/harvest?summary=1` and `/building/{building_id}`, beside the layer credits rather than instead of them. | **Yes, if you serve South Africa.** `0.19.0` said nothing changes for a country whose source permits export, and that is no longer true of South Africa: Statistics South Africa supplied the acknowledgement they accept on 20 October 2026, so it is in the pack and in every response with room for it. Show `text` under a map and `statement` on a licence or about screen. Read it once at boot from `/v1/places/generation` — `/search`, `/areas/search` and `/harvest` without `summary=1` answer with a bare JSON array and cannot carry a credit, and changing those shapes inside v1 would break every client that reads them. **Correction to this repo's README:** it said Stats SA's conditions require that derivative products be vetted before publication. Stats SA withdrew that clause on 20 October 2026 — it was a template sentence never applied to any product — and the README no longer says it. |
| `0.20.0` | 2026-10-16 | `kind` gains **`subdistrict`**, and the vocabulary is explicitly per country: a `kind` is the word a source uses for a level, and an `adm` code in a `kind=` parameter now resolves to whichever word that country's pack uses. South Africa's ADM3 is a `municipality`; India's is a `subdistrict` — a taluk, which is not a municipality in any sense. | **Yes, if you branch on `kind`.** Branch on `adm` instead: it is the comparable level and does not change. `kind=ADM3` keeps working and now means the right thing in each country; the literal `kind=municipality` still works where that is the word, and finds nothing where it is not. Nothing changes for a single-country client reading South Africa. |
| `0.19.0` | 2026-10-16 | A pack may **withhold its geometry**: where the source's conditions forbid redistributing boundaries, `/v1/places/geojson`, `/area/{area_id}/geojson` and `/street/{street_id}/geojson` answer **`403 geometry_not_served`**, naming the country and the source to credit. A pack whose source requires acknowledgement adds its credit to `attribution` on `/point` and `/area/{area_id}`. | **Yes, if you draw boundaries or show attribution.** `/point` still resolves a coordinate to a cell and `/areas/search` still returns cells and parents — only polygons are withheld, so a map layer needs a fallback for such a country while a cell picker does not. Credits already arrive as an array; a pack-level one simply joins the layer ones. Nothing changes for a country whose source permits export. |
| `0.18.0` | 2026-10-15 | A cell may have **no geometry**: a pack can hold a cell's name, codes and parent chain without a polygon. `bbox` is **omitted** on such a hit rather than returned as nulls. `within` resolves by ancestry when its target has no geometry, and refuses with **`400 within_unsupported`** when the target has neither geometry nor anything claiming it as a parent. | **Yes, if you use `within` or read `bbox`.** `bbox` is now optional on an `/areas/search` hit — a client that indexes it unconditionally will read undefined. And a constrained search can now refuse: treat `within_unsupported` as *this pack cannot answer that question*, not as an empty result. Needed because the lawful boundary source for some countries has no cell at the level a host needs, so the names exist and the polygons do not. |
| `0.17.1` | 2026-10-15 | Prose, and **one schema correction**. `info.description` defines a *host*: a platform that builds Places into its own product and calls this API from its backend on its members' behalf. **`PointResponse.place` gained `type: object`** — in OpenAPI 3.0 `nullable` does nothing without a type, so this is the first version that documents that field as nullable at all. The wire shape never changed; the document caught up with it. | **Only if you generate types from this document.** Under a strict generator `0.17.0` could emit `place` untyped or non-nullable, and the correction lands in your code as a type change. A hand-written client that already treats it as nullable needs nothing. Found by a host diffing a release we had called editorial — see the rule above. |
| `0.17.0` | 2026-10-15 | `/v1/places/generation` gains `contract`, the version of this document the deployment implements, and every response carrying `x-places-generation` carries `x-places-contract` too. | **Yes, if you pin a version.** Compare it at boot against the version you vendored and refuse below your floor with its own reason — the server is older than your app expects — never a claim about geography. A rollback past your floor was previously invisible: it would serve a contract you had not pinned and every call would look fine. CI asserts the reported version equals this document's. |
| `0.16.0` | 2026-10-15 | `/health` gains `build`: an opaque twelve-character fingerprint of the deployed build, not the image tag — the tag is a commit sha and `/health` is public. | **No.** Additive and diagnostic. It exists because a deploy that pulled nothing and restarted nothing was indistinguishable from one that worked — our smoke test passed for both. Useful to you only if you want to assert which build you are talking to |
| `0.15.2` | 2026-10-15 | Fix. 0.15.0 and 0.15.1 were not valid YAML: some inline `description` values held commas and `{id}` unquoted, so a strict parser rejected the file and a lenient one read part of a description as an extra property. Those values are quoted now. `PointResponse.place` gains `type: object`, which OpenAPI 3.0 requires next to `nullable`. Nothing the API accepts or returns has changed. | **Yes, if you vendored 0.15.0 or 0.15.1.** Take this one: generating a client from those versions fails or adds bogus fields |
| `0.15.1` | 2026-10-15 | Editorial. The contract no longer names a particular host or operator: `info.description` is general and `info.contact` is "Fascia Places". | No |
| `0.15.0` | 2026-10-15 | `/v1/places/coverage` gains `layers`: per-layer presence, read from the data. `false` means a layer is **absent**, not empty. Every key is present either way, including for a configured country with no ingest, where all read false. | **Yes, if you render a zero as "none here".** `[]` from `/streets`, `count: 0` from `/neighbours`, a missing `stats`, no building candidates — each of those is identical whether the layer is absent or empty. A host asked for this as a gate before an India pack, which will be partially ingested by design |
| `0.14.1` | 2026-10-15 | Editorial. The production server is `https://places.fascia.network`. The previous hostname serves the same deployment and the same host keys until hosts have moved, then retires. | **Yes, once.** Move your base URL. **If your vendored copy is older than 0.14.0, read that entry first:** it changed how a `404` must be handled. A host coming from 0.13.1 found a client that mapped every `404` to "country not served" |
| `0.14.0` | 2026-10-01 | A path that does not exist answers `404 not_found` rather than `401`, with or without a host key. Switch on `error.code`, never on the status alone: `no_pack_for_country` is a settled answer about a country, `not_found` is a path this deployment does not have. | **Yes, if you map statuses.** A client that read `404` as "no pack" would tell a user their country is unserved when a developer typed a path wrong |
| `0.13.1` | 2026-10-01 | Editorial. Removed a key-shaped example string from the security scheme; listed the production server. First published version. | No |
| `0.13.0` | 2026-09-30 | Not published. `404 no_pack_for_country` on every read for a country with no pack, asserting no generation; `loaded` on `/v1/places/generation`; `country` and `generation` on `/v1/places/layers`. | n/a — superseded by 0.13.1 before publication |
